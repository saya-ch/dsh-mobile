# Pairing, devices and cookies

## Pairing codes

A pairing code authorizes exactly one device. It is generated by the panel, consumed once, and expires.

- **Format**: 43 characters of base64url, from 32 random bytes.
- **Lifetime**: `pairingTtlMs`, default **120 000 ms (2 minutes)**, configurable 10 s–600 s. The iroh channel uses **5 minutes**. The link itself carries no expiry; the server-side window decides.
- **Storage**: gateway process memory only, as a SHA-256 digest plus an expiry. **Nothing is written to disk.** Restarting DSH or closing the gateway invalidates it.
- **Invalidation**: opening a new window replaces the old one; a successful pairing consumes it; expiry, device reset and gateway close all clear it.

### What the panel produces

`token`, `expiresAt`, `appKey`, `pairUrl`, `appPairUrl`, `loopbackPairUrl?`, `qrSvg`.

- `appKey` is `dsh1.<instanceId>.<token>` or `dsh2.<instanceId>.<token>`.
- `dsh2.` means "this entry uses a self-signed CA, so the phone must pin it"; `dsh1.` is a public-trust or LAN entry. **These prefixes belong to ordinary app pairing and have nothing to do with iroh**, whose QR is a JSON descriptor.
- `pairUrl` is `<origin>/mobile-access/pair#<fragment>`, where the fragment is `key=<appKey>` for a CA-pinned entry or `instance=<id>&token=<token>` otherwise.
- The browser page only reads the `token` fragment, so a `#key=` link is for the Android app; a browser user must paste the 43-character code.

The pairing page and its script exist **only while a window is open**; otherwise they return 404.

### App and browser endpoints

| Endpoint | Purpose |
|---|---|
| `POST /mobile-access/auth/pair` | Browser pairing → 201 with session and CSRF cookies |
| `POST /mobile-access/auth/renew` | Browser renewal using the device cookie |
| `POST /mobile-access/auth/native-pair` | App pairing → device token, session token, CSRF token |
| `POST /mobile-access/auth/native-renew` | App renewal |
| `POST /mobile-access/auth/native-probe` | App credential probe |
| `POST /mobile-access/auth/logout` | Clears session and CSRF cookies |

Failure codes: `invalid_request` (400), `authentication_failed` / `device_revoked` / `device_expired` (401), `forbidden` (CSRF, 403), `device_limit` (409), `rate_limited` (429, 8 attempts per 60 s per source), `not_found` (404).

## Device store

Two separate files, same schema:

- LAN: `<state>/devices.json`
- Remote (all channels): `<state>/remote/devices.json`

```json
{"version":2,"devices":[{"id":"<32 hex>","label":"<1-64 chars>","tokenDigest":"<sha256 hex>","createdAt":0,"expiresAt":0,"lastSeenAt":0,"nativeInstanceId":"<64 hex, optional>"}]}
```

What is **not** in it: the device token itself (only its digest), the origin, the certificate, a paired-at field (`createdAt` serves that role), or any iroh endpoint id. Those live in the iroh transport's own `paired.json`.

Defaults: 32 devices, 90-day device TTL, 8-hour session TTL, 64 sessions.

### Revoking

Revoking deletes the record outright (no tombstone), persists the store, ends that device's sessions, and tells the gateway to drop its live connections. It returns 404 for an unknown id.

It does **not** touch the iroh transport's `paired.json` — device tokens and transport peers are separate authorizations.

`devices/reset` with `{confirm:true}` clears every device, session and pairing window for that store. The remote reset additionally deletes `<state>/remote/devices.json`; it never touches the LAN store.

## Cookies

The serializer emits these attributes in fixed order: `name=value`, `Path`, `Max-Age`, `SameSite=Strict`, `Priority=High`, then `Secure` when the listener is TLS and `HttpOnly` when the cookie is a credential.

- **No `Domain`** — every cookie is host-only.
- **No `Expires`** — only `Max-Age`.
- `SameSite=Strict` always.

| Cookie | HttpOnly | Path | Notes |
|---|---|---|---|
| `dsh_ma_session` | yes | `/` | Session credential |
| `dsh_ma_csrf` | **no** | `/` | Page script reads it and sets the `x-dsh-mobile-csrf` header |
| `dsh_ma_device` | yes | `/mobile-access/auth/renew` | Renewal credential, deliberately narrow |
| `__Host-dsh_ma_session` / `__Host-dsh_ma_csrf` | yes / no | `/` | TLS variants, `Secure` |
| `__Host-dsh_ma_device_id` | yes | `/` | Device id, not a credential |

CSRF header name: `x-dsh-mobile-csrf`.

There is no cookie covering the whole site, and the device cookie only reaches the renewal path.

## The iroh descriptor

Encoded as JSON, not a URL. Ten fields, exact set, no extras:

| Field | Meaning |
|---|---|
| `version` | `1` |
| `type` | `dsh-mobile-iroh-pairing` |
| `endpointId` | 64 lowercase hex — the sidecar identity |
| `origin` | `https://<first32>.<last32>.iroh.localhost:<localPort>` |
| `localPort` | 1024–65535; currently 25443 |
| `irohCode` | 6 digits — transport authorization |
| `gatewayToken` | 43 base64url characters — device authorization |
| `caCertificate` | base64 DER of the CA the phone pins, ≤1536 bytes |
| `instanceId` | 64 hex; the CA fingerprint |
| `expiresAt` | epoch ms, at most 10 minutes ahead |

The descriptor must not exceed 2200 bytes. The phone pairs the transport with `irohCode`, then exchanges `gatewayToken` through the ordinary pairing endpoint for device credentials.

Treat it as a secret: it carries both the code and the token.
